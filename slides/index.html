先從一個情境開始

你丟一堆 PDF 給 AI，問了一個問題。
隔天再問一次，它記得昨天整理過的東西嗎？

現在常見的做法：RAG Retrieval-Augmented Generation

每次提問時，先從文件裡找出相關片段，再交給 LLM 寫答案。

NotebookLM、ChatGPT 上傳檔案多半是這樣。

問題

每一次都從原始片段重新推導。昨天整理出的關聯、發現的矛盾，今天都要重來一次——沒有東西被累積下來。

Wiki：overview、wiki-accumulates-rag-rederives來源：S1
核心想法

LLM Wiki：把「整理」從提問時，移到資料進來時

LLM 逐步建立並維護一組互相連結的 markdown 頁面。每讀一篇新資料，就把它整合進既有頁面：寫摘要、補交叉引用、標出矛盾。

RAG

像每次考試前才翻課本找答案

LLM Wiki

像每上完一堂課就把筆記整理好，下次直接看筆記

關鍵字：compounding（累積）——wiki 會隨著資料增加越來越完整，而不是每次重算。

結構

三層結構：誰可以改什麼？

Raw sources原始資料：文章、論文、圖片。只讀不改。人挑選
Wiki摘要頁、概念頁、比較頁、總覽，互相連結LLM 寫，人讀
Schema規則檔（CLAUDE.md / AGENTS.md）：頁面格式、命名、流程人 + LLM 一起改

每個 wiki 頁通常有：frontmatter（標題、類型、來源、日期）＋一句話 TLDR ＋內文＋反方論點或資料缺口。

為什麼現在才可行

人會放棄 wiki，是因為維護太累

以前

維護成本（更新連結、歸檔、改索引）長得比價值快，最後沒人維護。

現在

LLM 不會厭倦這些 bookkeeping，維護成本趨近於零。

人負責LLM 負責
挑來源、問好問題、判斷「這代表什麼」摘要、交叉引用、歸檔、更新索引
Karpathy 的比喻：Obsidian 是 IDE、LLM 是 programmer、wiki 是 codebase。
Wiki：llm-makes-maintenance-cheap、tool-stack來源：S1
代價與風險

wiki 寫得越有把握，錯的時候越難被發現

漂移 drift

新資料沒整合進來，舊綜整悄悄變錯，但讀起來仍很有把握。過時的 wiki 像錯誤資訊；過時的資料庫只像「不知道」。

規模 scale

原始提案：約 100 個來源內，靠 index 就找得到頁面。評論與教學文則認為 100–200 頁 index 就塞不進 context（說法不一，wiki 採信原始提案）

出處 provenance

頁面是 LLM 的詮釋，讀者分不清是誰的理解。

內化不足

LLM 負責寫、人只負責問 → wiki 很整齊，人卻沒學到。

Wiki：failure-modes 與 3 個主張頁來源：S1、S2、S3
怎麼改善

三個方向：可追溯、早發現、可重建

做法解決什麼
每句話標出處；不可變的原子筆記 + 穩定 ID出處不明
每個主張帶 confidence / status，ingest 當下就抓矛盾漂移、矛盾
以資料庫為準，從它重新生成 wiki錯誤累積
機械工作（建 index、切分）交給程式格式漂移
歸檔前自己先想清楚，並複核每一頁內化不足

檢查一下你懂了沒

Q1. RAG 和 LLM Wiki 最大的差別在「整理」發生的時間點，各是什麼時候？

RAG 在提問時整理；LLM Wiki 在資料進來 (ingest) 時就整理，所以會累積。

Q2. 三層結構裡，哪一層 LLM 只能讀、不能改？

Raw sources（原始資料）。

Q3. 為什麼說「過時的 wiki 比過時的資料庫更危險」？

wiki 是寫好的綜整，過時了仍讀起來很有把握，像錯誤資訊；資料庫只是查不到，看起來像「不知道」。
Wiki：wiki-accumulates-rag-rederives、three-layers、stale-wiki-looks-like-misinformation來源：S1、S2
重點回顧

帶走三句話

  • LLM Wiki = 讓 LLM 持續維護互相連結的筆記，知識會累積，不必每次重算
  • 三層（raw / wiki / schema）＋三個操作（ingest / query / lint）
  • 代價是成本前置與漂移風險：要標出處、早抓矛盾，而且人要自己想過
